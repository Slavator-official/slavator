# Бэклог развития Славатора

Формат прежний: MUST / SHOULD / COULD / WON'T / «Я рекомендую».

---

## MUST — живая расшифровка встречи

Слушать встречу в реальном времени, пока она идёт, и показывать расшифровку
по ходу. Пользователь сам находится в звонке на том же компьютере.

### Что делает

Два источника звука на выбор:

- **Микрофон** — слышно только пользователя и тех, кто рядом. Годится для
  очной встречи, для звонка бесполезно.
- **Звук компьютера** — слышно всех участников звонка. Основной сценарий.

Во время встречи: таймер, индикатор записи, живая осциллограмма и лента
реплик. Реплика появляется сразу текстом, имя говорящего подставляется
через пару секунд, когда диаризация догоняет. По остановке — обычная
обработка и сохранение в записи.

Макет готов: экран «Живая встреча» в прототипе
<https://claude.ai/code/artifact/38f6c733-e5fd-40b7-9582-74f7fba13900>

### Чего делать НЕ надо

Подключение к встрече по ссылке. Идея была прислать в приложение ссылку на
Телемост, чтобы оно само слушало. Так не выйдет: ссылка не даёт доступа к
звуку, чтобы слышать встречу — надо в неё войти участником. Otter и Read
держат для этого ботов, заходящих в звонок; у Телемоста публичного API под
это нет, а поднимать headless-браузер под учёткой пользователя — хрупко и
против правил сервиса.

Задача снимается не потому, что сложна, а потому, что пользователь и так
находится в звонке на этой же машине. Ссылка не нужна: нужен системный звук.

### Как захватывать системный звук

Исследование проведено 29.08.2026 на целевой машине.
Состояние: macOS 26.6.2, Python 3.12.14, разрешение на запись экрана выдано,
виртуальных аудиоустройств нет — из входов только «Микрофон MacBook Air».

**Путь А. ScreenCaptureKit** — рекомендуемый.

- `pyobjc-framework-ScreenCaptureKit` 12.2.2 есть на PyPI, требует Python ≥3.10.
- Разрешение на запись экрана уже выдано, оно же покрывает системный звук.
- Пользователю не нужно ничего устанавливать и настраивать.
- `SCStreamConfiguration.excludesCurrentProcessAudio` отсекает звук самого
  приложения — иначе воспроизведение образцов попадёт в запись.
- Риск: приём PCM из `CMSampleBuffer` через pyobjc не проверен.
  `CMSampleBufferGetAudioBufferListWithRetainedBlockBuffer` может оказаться
  плохо связан с Python. **Это первое, что нужно проверить прототипом**, до
  всей остальной работы.

**Путь Б. BlackHole** — запасной.

- Виртуальное аудиоустройство, ставится пакетом, лицензия MIT.
- Реализация тривиальна: обычное устройство ввода для `sounddevice`.
- Цена — настройка руками: установка с правами администратора и создание
  Multi-Output Device, иначе пользователь перестаёт слышать звонок.
  Для программы, которую передают коллеге одним файлом, это плохо.

Решение: сначала проверить путь А коротким прототипом. Если извлечь PCM не
удастся — путь Б с мастером настройки в интерфейсе.

### Что ещё продумать

- **Задержка против точности.** Диаризация работает по целому файлу.
  В живом режиме придётся либо разделять голоса по скользящему окну и
  уточнять задним числом, либо показывать текст без имён, а имена
  проставлять после остановки.
- **Длинные встречи.** Час живого звука — это память и накопление контекста
  для LLM. Нужна нарезка и промежуточное сохранение, чтобы падение на 55-й
  минуте не стоило всей встречи.
- **Приватность.** Захват системного звука пишет всё, что звучит на машине,
  включая личные уведомления. Индикатор записи должен быть постоянно виден,
  остановка — в один клик.
- **Согласие участников.** Запись звонка без предупреждения — юридический
  риск. Как минимум напоминание при старте.

### Критерии готовности

- [ ] Прототип на 20 строк подтверждает, что PCM из ScreenCaptureKit доходит до Python.
- [ ] Выбор источника: микрофон / звук компьютера.
- [ ] Расшифровка идёт по ходу встречи, отставание не больше ~10 секунд.
- [ ] Имена подставляются задним числом и не мигают.
- [ ] Остановка сохраняет встречу в общий список записей.
- [ ] Индикатор записи виден всё время, пока идёт захват.
- [ ] Звук самого приложения в запись не попадает.
- [ ] Часовая встреча обрабатывается без потери данных при сбое.

## Рядом лежит: что уже в работе

- **Перенос интерфейса из прототипа в Tk.** Прототип согласуется, дальше
  переносятся голосовая лента, палитра спикеров, плеер и вычищенные подписи.
  Тени и плавные переходы в Tk упростятся.
- **Прослушивание голосов** — кнопки воспроизведения в списке спикеров, в
  карточке человека и в новых голосах, плюс мини-плеер с перемоткой.
- **Голосовая лента** — визуализация диаризации. Данные уже есть в
  `diarization.json`, пользователю сейчас не показываются.

## Я рекомендую

- Оценить путь А одним вечером до планирования остального: он определяет,
  будет ли живой режим работать без настройки руками. От этого зависит,
  можно ли вообще отдавать приложение коллегам одним файлом.
- Живой режим и запись файла должны сходиться в одну и ту же обработку,
  иначе получится два пайплайна с расходящимся качеством.
